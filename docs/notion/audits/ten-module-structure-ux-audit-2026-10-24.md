## 核對方法與計數定義

1. 逐頁 Fetch 十個舊功能頁；抽取所有 `<database url=...>` 參照，檢查它們是否指向不同區塊（結果 76/76 不同 block IDs）。
2. 對**全部 76 個** Linked Database 區塊再 Fetch，核對各 block 的 Data Source、View 名稱、型別、篩選、排序及可見欄位數。合計 **177 個 View 設定**（不是177個獨立資料來源、也不保證各 View 互不相同）。
3. 將 block 背後 Data Source 去重後，得到 **23 個不同 Data Source**；逐一 Fetch Schema，彙整 **636 欄，其中152 Formula、147 Relation、48 Rollup**。其餘欄位含標題、狀態、日期、選項等。
4. 敏感資訊最小化：只記結構、非識別性的數量、篩選描述與必要的檢視 URL；不保存個案姓名、電話、會談、收據、薪資等原始資料。

## 優先發現：有結構證據的問題與待核實風險

### F-01｜活動「報名中」檢視條件與名稱相反（高優先，B）

- 本頁「🪩 活動管理」→ `view://3b08ca66-aa4d-8216-8abf-08275d9b29bb`，名稱「報名中」，現行篩選**`狀態 status_is_not 開放報名`**。
- 這在邏輯上會排除「開放報名」，與檢視名稱相反；**目前查詢回傳0筆**，因此還沒有實際漏列案例的證據，但篩選定義已明顯值得修復。
- **擬議 B 級修法**：先以當期 Events `狀態` Schema 選項確認「報名中」應有哪些狀態，隔離 TEST 放入「開放報名／未開放／取消／已完成」各一筆，將條件調整為明確所需值；不可直接在沒有測試時改正式 View。

### F-02｜「進行中活動」實際為「尚未完成群組」（中高優先，B）

- `view://9768ca66-aa4d-82d2-8284-8840f61fd407`，名稱「進行中活動」，固定篩選 **`狀態 status_is_not [Complete 狀態群組]`**；規則可能納入規劃、未開放或其他尚未完成狀態。
- 目前查詢0筆；**無法判斷實際影響規模**。
- **擬議 B 級**：明確界定「進行中」的核定狀態後用正向篩選；若本意是全部未完成，則改名「尚未完成活動」，避免錯誤理解。須確認目前 Status 選項再實作。

### F-03｜「本週會議」混入未篩本週的專案檢視（中高優先，B）

- 「09 Projects & Meetings」同區兩表：一張指向 Meetings 的週行事曆，另一張指向 Projects 的 `ALL` Board + 「進行中／已完成／規劃中」 Gallery；後者沒有按「本週」日期條件。
- **擬議 B 級**：保留 Meetings 與 Projects 分工，但將第二張獨立標題為「專案進度總覽」，避免標示本週卻展示所有專案。先在 TEST 複本比較導航。

### F-04｜標題重複≠資料來源重複（不要合併）

- Billing 的「待處理收據」兩表其實是 Receipt Requests 的「待審核」與「需人工確認」；「待建立收款」兩表分別是 Sessions 與 Event Registrations，不可合併計算。
- Events & Groups 的兩個「🚦待處理」其實分別是團體場次待建立 Sessions 與團體待建立場次；兩個「報名中」分別是 Group Therapy 與 Events，不能互相代替。
- Staff 的三個「待建立薪資單」依序涉及 Staff 待建立總覽、Payroll Statement 待拆明細、待生成PDF：不同工作階段，不能刪一留一。
- **擬議 B 級**：僅改善各任務入口的名稱與視覺分層，保留資料來源、View 和流程，減少錯誤導航。

### F-05｜「ALL」檢視可能只包含某些狀態（中優先，B）

- Tasks「任務管理-依任務類型」的 `ALL` 是 `Done=false`；Documents「待更新/草稿」的 `ALL` 實際只包含「待更新」與「草稿」；它們不是所有歷史資料。
- 某些 Billing `ALL` 也用必填檢查 Formula 作為固定篩選，是**該業務區段的 ALL** 而非資料來源的 ALL。
- **擬議 B 級**：保留各檢視的實際篩選，僅將字面「ALL」更名為「全部未完成」／「待更新＋草稿」／「此任務全部」，並核對是否可能誤導行政使用者。切勿直接清空篩選使敏感歷史資料浮出。

### F-06｜待確認條件：同意書、公式告警及「已預約」（中優先，僅建議 TEST）

- 「同意書未簽」 View 在 Care Episodes 的 `同意書簽署` 使用 checkbox_is 且 value 以 `null` 表示。需以隔離測試確認是否正確代表未簽／未填；不可見到 null 就直接判斷篩選錯誤。
- 多個「⚠️必填檢查」使用 Formula 條件、Rollup 或複合篩選。Notion 原生結果值無法只憑公式欄名與 View 判定正確性；需隔離 TEST 真值核對。
- Sessions 有「今日」依預約時間篩選、週/月只看「已預約」、另有「ALL」也限定「已預約」。這些可能是各區段預約管理的刻意安排，改名前需依操作情境確認。
