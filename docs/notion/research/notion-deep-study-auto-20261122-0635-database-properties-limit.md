## 來源核對與推論

1. 每個 database 最多500個 properties；超出時不能新增。不能把多個 Data Source 的欄位總和誤當成單一資料庫已達上限。
2. `Property visibility` 是在資料庫 View 顯示／隱藏欄位的操作，不能據此推論使用者沒有讀取該欄資料的權限。
3. `ID` 是自動生成且不可手動修改的數值 ID；不能未驗證便當作跨資料庫、跨匯入／重建都穩定的業務唯一鍵。
4. `Created time`、`Last edited time` 自動更新；不可把最後編輯時間當成方案核准、實際收款或服務日期。
5. Conditional color 設於 View 層；不同 View 不會自動同步，但複製 View 會複製顏色設定；色彩不是業務驗證或權限控制。
6. Formula、Rollup、Button、Unique ID 等欄位不支援欄位留言；不能假設每個欄位都能留下逐筆人工核准證據。

## 獨立反例／待驗假說

- CE01：看到整體23個來源合計636欄，就誤報單庫超過500欄。
- CE02：只隱藏敏感欄位，便錯認心理師不能透過其他 View 取得該資訊。
- CE03：把自動 ID 當成個案×期別的複合唯一約束，造成重複用量紀錄未被辨識。
- CE04：將最後編輯時間當作已完成會談的實際發生日，錯算核定期間。
- CE05：某個 View 的紅色條件著色被當成全工作台一致的超額警示。
- CE06：複製 View 後保留過期著色規則，造成新年度額度錯誤提示。
- CE07：要求在 Formula/Rollup 欄留言作為人工審核證據，但該類型不支援。
- CE08：達到單庫500欄上限時繼續擴充年度專用欄位，導致新增失敗並加重維護負擔。
